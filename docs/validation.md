# 验证体系

## 现状

```
Tier 1  静态验证      ✅ 已建立    scripts/validate.py   免费 · <2s · 不联网
Tier 2  行为验证      ❌ 未建立    真实会话跑每个技能
Tier 3  判断质量裁判  ❌ 未建立    LLM 给文档/输出打分
```

**这意味着**：能证明文件干净、结构自洽；**不能**证明技能给出的建议是对的。所以套件状态是 `DONE_WITH_CONCERNS`。

---

## Tier 1：11 项静态检查

| # | 检查 | 抓什么 |
|---|---|---|
| 1 | frontmatter 合法且 name 与目录一致 | 技能加载失败、路由找不到 |
| 2 | SKILL.md 与模板一致 | 文档漂移（手改生成物） |
| 3 | 凭据扫描 | API key、token、私钥、硬编码密码 |
| 4 | 隐私扫描 | 手机号、身份证号、邮箱 |
| 5 | 内容不含联网/提权/破坏性命令 | 意外的网络调用、`sudo`、`rm -rf` |
| 6 | 启动块只读 | 每次调用都改盘的副作用 |
| 7 | 路由表与实际技能双向一致 | 路由到不存在的技能、技能没被路由 |
| 8 | references 引用有效 | 指向不存在的文件 |
| 9 | 体积 ratchet | 文件无界膨胀 |
| 10 | SECURITY.md 声明齐全 | 安全承诺被悄悄删掉 |
| 11 | shell 语法与变量引用 | 语法错误、`$VAR（中文）` 粘连 |

```bash
python3 scripts/validate.py           # 全部
python3 scripts/validate.py --quiet    # 只看失败
```

## 对抗性验证（必做）

**一个只会说 PASS 的验证器没有价值。** 加任何检查规则时，用最小复现证明它能抓到目标问题。

已验证的对抗性用例：

| 注入 | 期望 | 实测 |
|---|---|---|
| 假 API key `sk-…` | 凭据扫描失败 | ✅ 抓到，退出码 1 |
| 假手机号 `138…` | 隐私扫描失败 | ✅ 抓到 |
| 手改生成的 SKILL.md | freshness 失败 | ✅ 抓到 |
| `$FOO（中文）` | shell 检查失败 | ✅ 抓到 |
| 连跑启动块两次 | 文件数不变 | ✅ 33 → 33 |

跑法见 `CONTRIBUTING.md`。

## Tier 2：行为验证（未建立）

**目标**：证明技能在真实任务里给出有用的输出。

**做法**（如果要建）：

1. 准备 5–10 个真实任务，覆盖六个技能
2. 每个任务记录：期望抓到的点、期望不抓的点
3. 用真实 agent 会话跑一遍，人工当裁判
4. 结果写成 `evals/<skill>/<case>.md`，记录输入、输出、判定

**成本**：每条用例一次会话；人工判定。

**为什么不自动化**：判断质量是主观的，自动打分容易变成"检查输出里有没有关键词"，那测的不是判断。

---

## Tier 3：LLM 当裁判（未建立）

**目标**：给技能文档本身打分（清晰度、完整性、可操作性）。

**门槛**：必须先有 Tier 2 的用例集，否则裁判没有锚点，打出来的分不可信。

**风险**：裁判模型可能偏好"写得自信"的文档，而不是"判断正确"的文档。这正是 gstack 被批评的点——**写得很自信的 skill 会自信地误导人**。所以 Tier 3 的分数只能当参考，不能当门禁。

---

## 回归纪律

1. 任何改动 → 先跑 Tier 1
2. Tier 1 全绿才算改完
3. **不要**为了通过而降低阈值、跳过用例、或重新判定失败
4. 失败要保留原始证据；区分"真缺陷"和"检查器缺陷"
5. 冻结代码后跑一次完整检查再报结果
